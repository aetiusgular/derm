# Contract: the events lane A emits, and the adapter record

Written by tk session 0, 27 Oct 2026, from the fork's receiver at `159ef3e` (`src-tauri/src/otel_receiver/decode.rs`, `normalize.rs`) and its recorded fixture `tests/fixtures/otlp/claude-2.1.302-logs.json` (copied into this repository). Lane A emits; lane B decodes.

## 1. How the receiver reads a record (read in code)

- The event name is the `event.name` attribute if present, else the record's `eventName`, else the body when it is a string (`decode.rs:25-57`).
- Claude Code 2.1.302 sends the **short** name in `event.name` (`tool_result`) and the prefixed name in the body (`claude_code.tool_result`): every record in the fixture does.
- `normalize.rs:42-46` strips `claude_code.` and `codex.` only. A name `pi.tool_result` with no short `event.name` would land as kind `otel.pi.tool_result`.
- `describe` (`normalize.rs:106-170`) maps short names to kinds: `tool_result` to `tool.call`, `tool_decision` to `approval`, `api_request` to `model.request`, `api_error` to `model.error`, `user_prompt` to `prompt`, `conversation_starts` to `session.start`, `assistant_response` to `message`.
- Attributes starting `user.` or `organization.` and `account_id` are dropped; `prompt`, `prompt_text`, `user_prompt`, `response` and `*.prompt` are dropped unless content logging is on (`normalize.rs:28-40`).
- The receive time is the event's time; the record's own time goes to `detail.harnessAt` (`normalize.rs:206-211`, review S4).

- No token, no POST. No endpoint, no POST. Nothing is sent anywhere but `DERM_OTLP_ENDPOINT`, which must be a loopback URL (`127.0.0.1`, `::1`, `localhost`); any other host is refused and counted.
- Under sbx, `derm run` rewrites the endpoint to `host.docker.internal:<port>` (lane D), which is not loopback, so the emitter refuses it and a Pi chat under sbx has no OTLP feed in wave 1. Integration w1 kept the loopback rule (lane D's request 1): widening it would let any `DERM_OTLP_ENDPOINT` an agent sets name a host on the network, and whether sbx's proxy keeps the `Host` header the receiver checks is not known. - Content off by default; hashes and sizes on.

## 4. The adapter record

Clients that are not OTel exporters (lane F's hook scripts, `derm run`) post `event` lines on the socket (`daemon-protocol.md`, section 2) with `source: "adapter"` (or `run`), their own `id`, and `detail.trust: "client"`. The id for a tool call is `<harness>-<tool_use_id>` when the harness gives a tool-use id, so the OTel record and the adapter record for one call can be joined (case 35: the last copy per id wins, within one chat; one call, two records, joined by `tool_use_id` in `detail`). Lane F's hooks post the decision as `kind: "approval"`, id `<harness>-<tool_use_id>-decision-<32 hex>` (`<harness>-unknown-decision-<32 hex>` when the harness gives no call id): the last part is 128 random bits from the core's `decisionId`, so the agent, which holds the same chat token, cannot post under that id first (integration w2's fix pass, box test w2 BW2; before it the id was `<harness>-<tool_use_id>-decision`, and call ids count up). Join a decision to its call by `detail.toolUseId`, never by the id; a second adapter decision for one call in one chat is kept as a conflict copy and flagged (`daemon-protocol.md`, section 2; FP1-S4). Written once per chat and id (S9: a later copy never replaces it), and the result as `kind: "tool.call"`, id `<harness>-<tool_use_id>`, with `resultSha256`, the size and the redaction count, never content. A hook posts only with a chat token (`contracts/policy.md` section 5).

### 6.4 The light tier's per-chat log (lane 6B; the line format for 6E)

- **Where.** With no daemon reachable (`gate/daemon.rs` `post_event` returned false), the gate appends the adapter record to `~/.derm/local/<chat>.jsonl`: the folder 0700, the file 0600, `<chat>` the chat id cleaned as `daemon::decision_id` cleans a call id (ASCII letters, digits, `_ . : -`; others `_`; at most 128), with `_` put in front of a cleaned id that is empty or starts with `.`, so no id names `.`, `..` or a hidden file (rules section 5, item 3). On Windows `:` also becomes `_`, and a device name (CON, PRN, AUX, NUL, COM0 to COM9, LPT0 to LPT9, in any letter case, with any extension) gets `_` in front (Microsoft's file naming rules); one function names the file for the writer and every reader (`gate::locallog::file_name`). A taint state for the chat sits beside it as `<chat>.taint.json`. Under srt `~/.derm` is denied to the harness (B8), so the light tier is the path without `derm run`.
- **One line per record**, the chain v2 format (below), written with a single `write` call (B5: `writeln!` on an unbuffered file makes several and tears lines), under `File::lock` taken with `try_lock` and a deadline below the hook's registered timeout (B4: 30 to 120 s registered; Grok's 5 s and Cline's 3 s are the tight ones); a pre event whose append fails is a deny unless the hook is part of a `derm run` chat (`locallog::denies`): a chat token with a real `derm run` above the hook (`gate::daemon::derm_run_chat`), whose record is the daemon's (case 86); a token alone does not count, since a project can set it (case 227; integration w6's review, W6C-S4), and the token must be the one `derm run` gave: the process `derm run` started on the way down to the hook was started with `DERM_CHAT_TOKEN` equal to the hook's (its start environment: `/proc/<pid>/environ` on Linux, `KERN_PROCARGS2` on macOS; not read on Windows, where the answer is no; re-review W6C-R6). Taint's fail-safe follows the same rule, and also counts a daemon that took the token on the call. Under srt the sandbox hides `derm run` from the hook (its PID namespace on Linux; its Seatbelt profile on macOS, read and not run, W6C-R8), so the answer there is no. **Open (re-review W6C-R7, run as root in the cloud):** under srt on Linux no hook reaches the daemon (srt refuses a Unix socket, FP2-L1), and srt's `denyRead` of `~/.derm` is a writable tmpfs, so the light log's append succeeds into a folder that goes with the sandbox: those records are kept nowhere and nothing denies. On Windows the file is opened read plus append, never append-only (`lock` fails with error 5), and a sharing violation (error 32) is retried within the deadline (AZ-8); readers open it with `FileShare.ReadWrite | Delete`, and still retry error 33 (`ERROR_LOCK_VIOLATION`) while a hook holds the lock: a Windows byte-range lock is mandatory, whatever the share mode (lane 6B, run in CI).
- **Chain v2** (`derm_core::audit_chain`, the reference, which the base wrote so 6B and 6E build against one format): `{"v":2,"seq":<n>,"prev":"<hex64>","kind":"<kind>","hash":"<hex64>","record":<object>}`, `hash` = SHA-256 over `derm-chain-v2\n<seq>\n<prev>\n<kind>\n<record as serde_json::to_string>`, keys sorted (serde_json without `preserve_order`), no floating-point number in a record (E2), `prev` of the first line 64 zeros, `seq` from 0. It fixes AZ-1: v1 hashed neither `seq` nor the key, so a relabel or a consistent renumber verified (B6). `verify` takes the start (`seq` and `prev`, for a file that does not begin a chain) and the anchored end; a tail cut or a whole rewrite shows only against an anchor (case 216). `kind` is the record's `kind` (`approval`, `tool.call`, `install.call`, `taint.mark`, `taint.review`).
