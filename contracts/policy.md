## 1. The file

- Path: `$DERM_POLICY` if set, else `~/.derm/policy.json`. User-level only. `derm` never reads a project-level policy file, because an agent can write one (rules section 5, item 4).
- Read lazily: no reader opens it at load or session start (corner case 46). Lane A reads it on the first `tool_call`.
- A missing file is the default policy: no rules, so every call is `ask` (section 4, step 4), and `ask` times out to `deny`. A file that does not parse, or fails the schema, is treated as missing and the reason says so. Nothing fails open.

```json
{
  "version": 1,
  "askTimeoutSeconds": 60,
  "servers": ["exa", "github"],
  "rules": [
    { "tool": "exa/*", "action": "allow" },
    { "tool": "fs/write_file", "chat": "chat-b", "action": "allow",
      "descriptionSha256": "475c1f1f..." }
  ]
}
```

| Field | Meaning |
|---|---|
| `version` | `1` |
| `askTimeoutSeconds` | How long an `ask` waits before it becomes `deny`. 1 to 3600, default 60 |
| `servers` | MCP server names the user connected, normalized by section 2, step 1 before use (so `my-server` matches `my-server_fetch`). Used only to split `{server}_{tool}` names (section 2, step 6) |
| `rules[].tool` | A normalized name (`server/tool` or a bare built-in), `server/*`, or `*` |
| `rules[].harness` | Optional. A harness id from the preset table (`crates/derm-cli/src/connect/presets/`) |
| `rules[].chat` | Optional. A chat id as the harness or `derm run` reports it |
| `rules[].action` | `allow`, `ask` or `deny` |
| `rules[].descriptionSha256` | Optional. SHA-256 hex of the approved tool description (case 57) |

## 2. Normalizing a tool name

Every harness spells an MCP tool differently (note AP section 4, note AQ section 6; corner case 60). The matcher normalizes before it matches. It is a function of the name, the `servers` list and the agent's id (`harness`); later waves apply an agent's declared name form from its preset row before these steps (note AQ section 6), and no wave 1 agent declares one. In order:

1. Trim; ASCII-lowercase; replace every character outside `[a-z0-9_/]` with `_`. The same step normalizes each `servers` entry.
2. If the name contains `/`, it is already `server/tool`: done (after step 7 on the server part).
3. `mcp__<rest>`: when a normalized `servers` entry `<s>` is the longest one `<rest>` starts with followed by `__`, the server is `<s>` (a listed server whose name holds `_` or `__`; integration w2); else split `<rest>` at the first run of two or more `_` (the whole run consumed), else at the first `_`. Claude Code, Codex, Pi, OpenClaude, Qwen Code 0.26.1, Hermes, Command Code, Kimi (`mcp__s__t`; note AQ section 9 corrects the earlier attribution of Qwen and Hermes to step 4).
4. `mcp_<rest>`: the same split. Gemini, Crush, Kiro's hooks (`mcp_s_t`).
5. `<a>__<b>`, split at the first run of two or more `_`: server `a`, tool `b`. Grok, Cline, Codebuff, goose, OpenClaw's bridge, MetaMCP (`s__t`), and Droid's binary (`s___t`).
6. `<a>_<b>` where `a` is the longest normalized entry of `servers` that the name starts with, followed by `_`: server `a`. OpenCode and Kilo (`s_t`), ToolHive vMCP (`{workload}_t`), and Copilot CLI's `<server>-<tool>`, which step 1 turns into `s_t` (note AQ section 9: Copilot is not `mcp__s__t`). A name with no such server is a bare built-in name.
7. A server named `plugin_<plugin>_<server>` (Claude Code's plugin servers, `mcp__plugin_<plugin>_<server>__<tool>`, read in Claude Code 2.1.311's binary) keeps its whole name: the normalized tool is `plugin_<plugin>_<server>/<tool>`, and only a rule naming that server (`plugin_derm_exa/*`) can allow it. Until integration w2 it became `<server>`, so any plugin shipping a server called `exa` inherited your `exa/*` allow (integration w1, security finding S5). Its bare forms are narrowing names (section 4, step 3a).

Anything else is a built-in tool by its bare lowercased name: `bash`, `read`, `write`, `edit`, `webfetch`.

Known gaps: a server name that itself contains `_` is ambiguous in steps 3 and 4 (Gemini's parser splits at the first underscore too: note AP section 4). Library entries and `derm connect` use server names without `_`. The forms note AQ section 6 lists as unhandled (Auggie's `<tool>_<server>`, Cursor's `MCP:<tool>`, dispatcher and code tools, Kiro's `@s/t`, Vibe's `mcp_s.t`) wait for the per-agent forms of waves 2 and 4.

Source: `normalizeToolName` and `narrowingNames` in the hook core (`packages/derm-claude-plugin/src/core/policy.ts`), `normalize_tool_name_for` and `narrowing_names` in `crates/derm-core/src/policy.rs`, `normalizeToolName` and `narrowingNames` in `packages/derm-pi/src/policy.ts`; fixture cases 1 to 12, 22 to 25 and 46 to 51.

## 3. The reject list

Run before any rule, on `fold(inputText)` and again on the same text with every `"` and `'` removed, because the shell joins `ANTHROPIC_"BASE_URL"` and `g''it` into one word (integration w1, security finding S1; fixture cases 34, 35). A hit is `deny`, whatever the rules say, with the reason `reject list: <key>`.

**The input text.** For a shell tool: the command, then on their own lines the values of every other field of the call except a free-text `description` (a working folder such as OpenCode's bash `workdir`, a timeout), each value that holds a `/` also once more with a trailing `/` so a folder meets the folder markers of section 4 step 7a (integration w1, finding S7). For any other tool: every key and every string, number and boolean value, one per line, unescaped (the hook core also adds the serialized JSON).

**Escapes** first: `\uXXXX` (JSON and TOML) and `\UXXXXXXXX` (TOML) are decoded, so a key a tool writes into a config file escaped is seen as the key it becomes (fixture case 28).

**Folding** (case 30, case 33), settled by integration w1 on the hook core's algorithm: NFKD; drop combining marks (general category Mn and Me); then per character: drop invisible and format characters (U+00AD, U+034F, U+200B to U+200F, U+2060 to U+2064, U+FEFF, U+180E); map every Unicode space (U+0085, U+00A0, U+1680, U+2000 to U+200A, U+2028, U+2029, U+202F, U+205F, U+3000) to one ASCII space; map fullwidth ASCII (U+FF01 to U+FF5E) to ASCII; map a confusable to its ASCII look-alike, one or more characters (Unicode `confusables.txt` 17.0.0, sha256 `091c7f82…ef22a`, from unicode-org/unicodetools at `578f6c0`); then lowercase and map once more. The three matchers give the same result on every one of the 194,432 non-ASCII code points (run 27 Oct; `fixtures/policy/fold.json` holds the 3,391 whose fold contains ASCII). The Rust tables are generated from the hook core's sources and Node's ICU (Unicode 17.0); `gen-fold-tables.mjs --check` fails when they drift.

## 4. Matching

1. Normalize the tool name (section 2).
2. Run the reject list (section 3). A hit is `deny`; stop.
3. Collect the rules that match: `tool` equals the normalized name, or is `<server>/*` with the same server, or is `*`; `harness` absent or equal; `chat` absent or equal.
   a. **Narrowing names** (integration w2, finding S5). The call's other possible names are: for a plugin server `plugin_<rest>`, `<bare>/<tool>` for every suffix `<bare>` of `<rest>` after a `_` (plugin and server names both hold `_` after step 1, so the split is not known); and for an `mcp__` or `mcp_` name, every other split of the remainder at a run of `__` (Claude Code allows a server named `<a>__<b>`, read in its rule hints). A rule (not `*`) that matches one of these, with `harness` and `chat` as above, narrows: a `deny` is the answer at once, reason `rule <tool> (also names <normalized>)`; an `ask` turns an `allow` from the steps below into `ask` with the same reason; an `allow` there counts for nothing. When a split past the primary's server exists (a longer server name no `servers` entry rules out), an `allow` becomes `ask`, reason `ambiguous server name`. Fixture cases 7 and 46 to 51. The same holds when the raw name does not spell the primary split plainly (integration w2's review, finding W2-S2): the server part has an ASCII capital or a non-ASCII letter, or the characters between server and tool are not the form's own separator as written (`__` after `mcp__`, `_` after `mcp_` or with no prefix, at most two underscores in the unprefixed run form), so `mcp__exa-__t`, `mcp__exa.__t`, `mcp__exa___t`, `mcp__EXA__t` and OpenCode's `exa-evil_t` are not `exa`'s; an agent's declared separator counts as plain (`RAW_SEPARATORS`, which lists only agents with a built gate: oh-my-pi's `_` after `mcp__`; Droid's `___`, Copilot's `-` and Mistral Vibe's `.` ask until their wave 4 lanes show the form folds in no other server, re-review W2-R1, cases 24, 25, 59, 60). Step 1 trims the characters JavaScript's `trim` does in all three matchers (U+FEFF trimmed, U+0085 kept). Fixture cases 54 to 60. **A shell under another name** (integration w4, lanes L and P's requests, case 82): a shell tool of step 7b's list other than `bash` has `bash` as its one narrowing name, so a `bash` deny denies Gemini's `run_shell_command`, Codex's `exec_command` and Claude Code's `Monitor`, a `bash` ask turns their allow into `ask`, and a `bash` allow widens none of them (fixture cases 70 to 73). 4. None: the answer is `ask`, reason `no rule`.
5. Rank the matches by, in order: `chat` set beats unset; then `harness` set beats unset; then the tool pattern, exact beats `server/*` beats `*`. The top rank wins. Among rules of equal rank the most restrictive action wins: `deny`, then `ask`, then `allow`. So a rule scoped to a chat overrides everything else for that chat, which is how a chat is locked down.

Every tied pin must hold (derm-core's rule; the TypeScript matchers took the first rule of a tie until integration w1's security finding S10).

An install whose every package is already in the project's lockfile at the same version keeps the `allow`; any other install is `ask`, the reason naming each package and its version or "no version" (lane X sets the wording; the fixture checks the names). The check never turns an `ask` or a `deny` into an `allow`, and an `allow` it does not read as an install is unchanged. Under full access the `ask` becomes `deny`, as every ask does (case 83). With the pre-install check on (off until the user turns it on, `settings.schema.json`'s `installs.check`; universal plan section 8, call 10), the daemon's answer can make it a `deny`: a name not in the registry (`not in the registry`, case 130) or an OSV `MAL-` record (with the record's id); a version younger than `installs.minAgeHours` (48 by default) or with a known vulnerability stays `ask`, with the reason.

## 7. Command rules (wave 5, lane W; decided at integration w5's phase 3 merge, 4 Nov 2026; built by lane W, 5 Nov 2026)

Lane W's policy presets need rules that name a CLI command, not only a tool (`plans/toolkit_universal_plan.md` lane W: `gh pr create` asks, `git push --force` asks or denies, case 135). Decided at the phase 3 merge; built by lane W as patch W-1 (`tests/cli-contract/checks/W/requests/`), in all three matchers (`command.ts` in the hook core and derm-pi, `crates/derm-core/src/command.rs`).

**The field.** A rule may carry `command`: an array of 1 to 8 words. The first is a command name, `^[a-z0-9][a-z0-9._:=+-]{0,63}$` (lowercase, as the matcher folds). A later word is either such a word or a flag, `^--?[a-z0-9][a-z0-9._:=+-]{0,61}$` (lane W's addition: the plan's `git push --force` needs one). `tool` must then be `bash` (a shell tool of step 7b's list maps to it, case 135), and the rule has no `descriptionSha256`. A rule with `command` and any other tool, or with a pin, fails the schema and every matcher. A flag as the first word is refused by the three matchers; the schema cannot say "the first item only" under the strict tuple rule its tests run with. `fixtures/policy/invalid.json` holds each refused shape.

**A command rule is never a rule for the whole tool.** It takes no part in steps 3 to 5 or 3a: a `bash` rule with `command` neither allows nor denies the shell. The writers of an agent's own rules (`derm connect <agent> --rules`, Gemini's printout) leave command rules to the gate and say so: as the agent's own deny one would take the whole shell away.

**How a deny or an ask matches (narrowing).** Only shell tools. The folded input (step 7a's text), as written and with every `\` removed, is split into simple commands at `;`, `&`, `|`, `(`, `)`, line breaks and backticks (`&&`, `||` and `$(` included), quotes joining words as the shell does (lane X's `commands`). In each, leading assignments are dropped; a wrapper of lane X's list (`sudo`, `doas`, `env`, `command`, `exec`, `builtin`, `nohup`, `time`, `stdbuf`, `chronic`, `unbuffer`, `nice`, `ionice`, `chrt`, `taskset`, `timeout`, `xargs`, `corepack`) is skipped up to the first later word that names a rule's first word, a wrapper or a shell; a shell's `-c` string (the first word that is not an option once `-c` is seen: `+x` options, the values of `-o`, `+o`, `--rcfile` and `--init-file`, and `--` are read as bash reads them; review W5-S3), `eval`'s words and `env -S`'s string are read as text of their own (four levels at most); `busybox` counts as a wrapper. A command's first word counts by its program name (`/usr/bin/git` is `git`). A rule meets a command when the first words are equal and each later plain word of the rule follows in order, past flags and one value after a flag (`git -C repo push` meets `["git", "push"]`; `git commit -m "push x"` does not). A flag word of the rule meets that flag anywhere after the plain words before it, as `--force` or `--force=...`, and a one-letter flag also inside a cluster (`-f` meets `-fu`); a long flag also meets a prefix of it of two letters or more (`--forc`, `--ha=x`), as git and other parsers take an unambiguous prefix (integration w5's close, review W5-S4). Reading more than the shell runs only narrows more.

**What a deny or an ask does.** A matching deny makes the call `deny` at once, before steps 3 to 5, reason `rule bash <words>`. A matching ask turns an `allow` into `ask` with that reason, and stops an allow command rule from widening.

**What an allow does (widening).** An `allow` command rule widens only a call that step 5 left at `ask` with reason `no rule`, or at a `bash` `ask` whose rank (chat, harness, tool, as step 5) is no higher than the command rule's, and only when the whole folded text is one plain simple command (none of `;&|()<>`, a backtick, a line break or `#`) whose first words are the rule's, in order and exactly: no wrapper, no path, no assignment before it; and every word after the rule's words is a plain operand, with no leading `-` and no `=` (integration w5's close, review W5-S1: `git log --output=<file>` under an allow for `git log` wrote a file through a committed link into `.git/config`). It never widens an install of section 6, never turns a `deny` into anything, never beats a `chat` or `harness` rule of higher rank, and never skips steps 2, 6, 7a, 7b, 7c or section 6: the widened call passes them as an allow would, or the ask stands with its own reason. A `bash` ask that narrows a shell under another name (step 3a) counts as the `bash` ask it may widen. Under full access (case 83) an `ask` is `deny`, as always. Of several matching allows, the one with the most words names the reason.

**Fixtures.** `fixtures/policy/policy.json` gains six command rules (two asks and denies on `git push`, a deny on `gh repo delete`, allows on `git status`, `gh pr view` for Codex, `npm install`); `cases.json` gains cases 85 to 106, run by all three matchers (and 107 to 116 from integration w5's close, with case 97 changed from allow to ask); `invalid.json` holds the ten refused shapes.

**Known limits** (lane W; the gate guards against a mistake, not an agent, case 89): a command reached through a script, a Makefile target, an alias, a function, `find -exec`, `ssh` or `watch` is not read (as installs reached indirectly, case 132); a force push by refspec (`git push origin +main`) has no flag word to meet; a flag's value that happens to equal a later rule word can satisfy it (`git -C push status` meets `["git", "status"]`, which only matters for narrowing).

## 8. Secrets the broker injects (wave 6, lane 6C; the wave 6 base, 12 Nov 2026)

Not in `policy.json`: the policy file keeps its four keys (section 1), and every matcher refuses an unknown one, so a secret there would make every call ask. The broker's list is its own file, `~/.derm/secrets.json` (`secrets.schema.json`), owner-only like the policy (case 226's checks), written only by `derm secret` from a terminal. It names secrets; it never holds a value.

- `derm secret add <id> --host <h> [--host <h>...] (--env <VAR> | --file <path> | --keychain <service>)`: `id` is `^[a-z][a-z0-9-]{0,31}$`; each host an exact lowercase name, no port, no wildcard. The value is read at chat start from where the entry says (the variable from `derm run`'s own environment, which the agent's then lacks; a 0600 file of yours; the macOS keychain or Linux's secret service), never written by derm anywhere but the egress proxy's memory.
- **8.1 Which chats.** Under the Standard tier or srt only (`run.start`'s `tier`): Claude Code through `network.httpProxyPort` or its own `HTTPS_PROXY` (C1), srt through `network.parentProxy` (C2), Codex through its own proxy's upstream (C3; AZ-11). Under sbx: none (case 218). Subscription sign-ins are out of scope (cases 181, 186, 190). The wave 6 plan's call 3 (API keys and CLI tokens for v0.2) stands as recommended until Tony says otherwise; provider keys through the tap (`derm-tap/src/broker/`) only if he chooses the wider option.
- **8.2 The placeholder** the agent holds: `dermsecret_<id>_<16 lowercase hex>`, the hex drawn per chat, so a placeholder from one chat means nothing in another. Letters, digits and `_` only, so it survives an environment variable, a header, JSON, a URL and a DNS label unchanged. The agent sees it where the value would have been (the variable `derm run` sets for the harness).
- **8.3 What the proxy does** (`derm_egress::decide`; red tests in `crates/derm-egress/tests/contract.rs`): a request whose CONNECT host is one of the secret's hosts, and whose TLS server name equals the CONNECT host, has the placeholder replaced by the value in its headers and body; the placeholder or the value anywhere in a request to any other host (a header, the body, the URL, or a label of the host name itself) blocks the request and records `secret.block` (case 217; `events.md` section 6.3); an SNI that differs from the CONNECT host blocks it. TLS is terminated with a local CA the person creates from a terminal (note AZ C8: blocking std::net, rustls, rcgen; not hudsucker), kept 0600 or in the keychain; each client needs its own trust variable (C4: `NODE_EXTRA_CA_CERTS` for Claude Code, `SSL_CERT_FILE` or `CODEX_CA_CERTIFICATE` for Codex, Go by the module's `go` line, `http.sslCAInfo` for Git for Windows), and on Windows the per-user store asks the person in their own session (C5), and schannel clients need revocation data or a stated flag (AZ-9).
- **8.4 As wired at integration w6's close** (13 Nov 2026; lane 6C's R1 with Tony's R2 and decision 2). derm-egress runs inside `derm run`, one per chat (`run/broker.rs`): the values are read there at the start (one unreadable value refuses the start; a missing CA, or one expiring within a day, refuses it too, naming `derm secret ca create`), never cross a socket, and end with the chat; its records reach the daemon over `derm run`'s daemon-scope connection as source `run`. The trust files are written to a fresh folder in the system's temporary folder, never under `~/.derm`, and removed at the end. Decision 2 as Tony settled it (12 Nov, 23:58 PST): a secret's value is swapped into a request's headers only, and into its body or query only where the entry's `placement` says so (`derm secret add --in body|query`; `secrets.schema.json`); toward a model host (the tap's table) a placeholder of another secret passes in the body, the conversation, only, and is blocked in the URL and the headers; the value is blocked there as anywhere. Response scrubbing (open item O3) is not in v0.2.
- **Prior art.** Claude Code's `sandbox.credentials`, srt 0.0.82's `credentials`, Codex's network proxy (placeholder injection, SigV4) and sbx each ship a broker (C7). The base's reading (plans/parallel/tk_w6_base.md, Decisions): derm runs its own for v0.2, so one placeholder form, one record set and one block rule hold on every tier it covers; lane 6C reads the vendors' brokers first and writes, under its Research, what each would lose or gain, and may request that derm drive one instead.

## 9. Taint (wave 6, lane 6D; the wave 6 base, 12 Nov 2026)

- **What taints a chat:** a result from a tool that fetches content (`webfetch`, `websearch`, an MCP tool of a server not marked trusted, a tool the gate does not know), or a read of a secret path. The tap's view of every result (`derm-tap/src/results/`) for tapped chats; PostToolUse where only hooks see results (D2). Results join hook records on the call id, Gemini by name and order (D3).
- **What taint reviews:** after a chat is tainted, a call to a host the chat has not reached before, a write to a control path (section 4, step 7a) or to a file the person marked protected, an install (section 6), a push, running a file the session wrote (E0's `session-written-code`, R-E0-6), and a command or host a tool result named (OpenMoat ADR-057), each given the chat's verdict. Taint only raises an answer: an `allow` can become `ask`, a `deny` stays; under full access an `ask` is a `deny` (case 83).
- **Which verdict, per chat** (Tony's call of 12 Nov on the wave 6 plan's call 2: all three, chosen per task). Taint lasts the whole chat, every prompt in it, since text read in one prompt can drive an action in a later one; so the verdict is a per-chat choice: `derm run --taint ask|deny|record` for that chat (recorded as `run.start`'s `detail.taint`, `events.md` section 6.2); else `~/.derm/settings.json`'s `taint.verdict`; else `ask`. `ask` reviews each tainted call; `deny` refuses it; `record` lets it run and writes `taint.review` with `wouldBe` (`ask`), for a task where the person accepts the risk or to measure false positives. The gate learns a chat's verdict from the daemon's record of its `run.start` (or, in the light tier, the setting alone), never from an environment variable, a project file or anything the agent can write: a project's settings can set a hook's environment (case 227). Anything else that names a verdict may only raise it (`record` to `ask` to `deny`), never lower it. On an agent that cannot prompt, `ask` is `deny` (case 71). The verdict holds for the chat; a change is a new chat.
- **As built by lane 6D** (request 6D-2, folded in at integration w6's phase 2 merge): running a file the session wrote (`session-written-code`) is reviewed whether or not the chat is tainted, as OpenMoat 0.19.0's `src/session_code.rs` does; derm does not skip it under a boundary, since a hook cannot read the boundary safely (case 227). A chat is marked when the gate decides the fetching call, not when its result arrives, since no seam derm owns sees a post event for 13 of 17 agents (note AZ D2): a fetch the person then declines at the agent's own prompt still marks the chat. The rule for hosts a result named (`named-in-result`) runs in the daemon tier only. Taint records only what it raised: a call the policy already asks about gets no `taint.review`. Under `derm run` the chat's state lives in the daemon (`op: "taint"`, `daemon-protocol.md` section 2); when the daemon refuses the op, the gate uses the light tier's file with the verdict `deny`, and with neither, taint is off for that call.
- **The named-host rule needs a key the agent cannot read** (D4): a fingerprint of a result's hosts and commands is kept in the daemon's memory, or under a key the agent's user cannot read; the light tier, which has no such key, applies coarse taint only and `derm status` says so.
- **Hosts** in a result and in a later call are read under both URL readings, WHATWG (the `url` crate, 2.5.8) and RFC 3986 (curl and git), and a match on any counts (D5: `a.test\@b.test` is `a.test` to the crate and `b.test` to curl and git).
- **Red tests:** `crates/derm-cli/tests/contracts_w6.rs`, lane 6D's, replay the five E0 scenarios `fixtures/eval/moatbench-e0-allowed.json` marks `owner: 6D` through `derm hook claude-code` with no daemon (the light tier's taint file).
