# Hook dialects: how each wave 4 agent runs derm's gate

Written by integration w2 on 28 Oct 2026, for wave 4's lanes L, N and P (`plans/parallel_build_tk.md`, section 7a). It turns note AQ section 4 (`research-notes/AQ_harness_coverage_matrix.md`, read 27 Oct) and a fresh read of each agent's docs and source on 28 Oct into one contract per agent: where the gate is registered, what it reads on stdin, how it answers, the switch that makes a failed gate block, and where an `ask` goes. Each agent has a fixture folder, `fixtures/hook-dialects/<preset id>/`, with a registration, the pre-tool input for a shell call (and an MCP call where the agent documents one), the replies it accepts, and `sources.json`, which says for every file whether it is the vendor's documented example verbatim or built from the documented fields, its source, and a mark. `contracts.test.ts` holds the folders to that shape.

Marks: **V** read in a primary source at the version named (docs, source at a tag, the npm tarball's code or bundled docs); **I** inference; **NF** looked for and not found. Nothing here was run against a real agent: integration w2 installed none of them. Each lane reads its agents' rows, checks them against the agent at the version it builds for (rule 6), and records any difference in its status doc; a difference that changes the gate is a request for integration, which fixes this file.

## 1. What every dialect does

Common to all sixteen, from section 7a and the corner cases:

1. **One decision, the core's.** The dialect turns the agent's input into the core's `{tool, input, harness, chat}` (`packages/derm-claude-plugin/src/core/gate.ts`, synced into each package), calls it, and turns `allow`, `ask` and `deny` into the agent's reply. The agent's tool name goes through the matcher with the agent's id, so its name form is preset data (`toolNameForm` in its preset file), not dialect code.
2. **Allow only where a rule says allow** (case 72). An agent where a hook's allow skips its own prompt gets an explicit allow only for a rule's `allow`; with no rule, the dialect gives the agent's "no decision" only where that does not run the call under the agent's own auto-approve mode, else the daemon approver or deny.
3. **Ask** (cases 71, 63): the agent's own prompt where it can show one (column "Own ask"), else the daemon approver's answer within the hook's timeout, else deny. Never "no decision".
4. **Deny one call, never the run** (case 79): each agent's per-call form; the run-ending forms are listed per agent and never used.
5. **Fail closed where the agent allows it** (case 70): set the switch in column "Fail switch" in the registration; where there is none the row says "fails open" and `derm status` shows it. Keep the gate fast: a timeout is the failure most agents let through.
6. **Output** (case 77): print only the agent's decision. Where stdout on success reaches the model (Kiro), print nothing on allow. Never echo the tool input.
7. **Token** (case 76): the chat token from `DERM_CHAT_TOKEN` or the 0600 file `DERM_CHAT_TOKEN_FILE` names, never `daemon.token`. Where an agent strips variables by name, the row says whether `DERM_CHAT_TOKEN_FILE` survives.
8. **Shell tools** (case 82): the agent's shell tool names map to `bash` in its preset file (`coverage.shellAliases`), so case 30's checks run.
9. **Beside Orca** (case 75): registered next to Orca's own status hook in the same file where Orca writes one, never replacing it; tests run with Orca's entry installed.
10. **Full access** (case 83): tests also run under Orca's full-access flag for that agent.
11. **User level only** (case 78): registration goes in the user-level file; `derm connect <agent> --gate` (lane Q) writes it under lane C's rules.

### 9.2 Whose input it is (BCR-7, case 109)

`derm hook <agent>` answers in `<agent>`'s dialect only when the input's own marks agree with argv. Grok 1.0.77 runs the hooks in `~/.claude/settings.json` and `~/.cursor/hooks.json` after folder trust, by default (its embedded docs' hook-locations table and `[compat.*] hooks = true`, read in its binary; BCR-7, V), and Cursor runs Claude Code's (case 109). A user-level `derm hook claude-code pre` registration therefore fires inside Grok and Cursor.

- The marks per dialect are what the TypeScript dialect reads today: Cursor's `cursor_version` with its camelCase event (`packages/derm-claude-plugin/src/hook.ts`, `runByCursor`, `cursorGateRegistered`); Gemini's `hook_event_name` `BeforeTool`/`AfterTool`; Copilot's camelCase fields with `toolArgs` as a JSON string (BC 2); Grok sends both spellings (BC 2).
- Input with another agent's marks gets case 109's answer: it defers, with no decision and no record, only when derm's own gate for that agent is registered and fails closed; otherwise it blocks and names the fix. It never decides in a dialect it does not speak.
- What marks a Grok run of a Claude Code hook carries is **NF**: lane 5bA records that input from Grok 1.0.77 (or the version it pins) before it builds the check, and until then a Claude-format input whose marks cannot be told apart is answered as the argv's agent and the doubt is in the lane's Not verified list.

### 9.3 How a Rust dialect is held to the TypeScript (the red tests)

The base recorded every hook call the TypeScript dialect tests make (`fixtures/hook-cases/record-setup.ts`, run through `record.vitest.config.ts`: 299 test cases, 528 calls at `e29ce27`) and turned them into one case file per lane (`fixtures/hook-cases/5bA.json`, 165 cases and 335 calls; `5bB.json`, 62 cases and 193 calls) with `gen.mjs`. `crates/derm-cli/tests/hook_cases_5bA.rs` and `_5bB.rs` hold one Rust test per case, built with the feature `w5b-red` until the wave 5b close and always since (`cargo test -p derm-cli --test hook_cases_5bA`). `tests/support/replay.rs` sets each call up as recorded (the temp folders and their files, the environment, stdin, a fake daemon in the recorded answer mode, an empty `HOME` where the case set none) and runs `derm hook <agent> <event>` with exactly that environment. A call passes when:

1. the exit code is the TypeScript's;
2. stdout is empty when the TypeScript's was, and otherwise each JSON line is equal to the TypeScript's after every string under a reason key (`reason`, `permissionDecisionReason`, `systemMessage`, `stopReason`, `user_message`, `agent_message`, `message`, `additionalContext`, `followup_message`) is cut to its first two words after `derm: ` (derm-core's reasons name the rule's action, `rule bash deny`, where the TypeScript's said `rule bash`; the wording is derm-core's from now on); a rewritten input (`updatedInput`, Hermes's `args`) is compared whole;
3. stderr's first line is cut the same way and equal;
4. the daemon lines after `hello` are the same sequence of `event` (kind, harness, decision, tool) and `approve` (harness, tool).

The harness was checked against the TypeScript itself: with `DERM_REPLAY_ORACLE=ts` it replays each call against the TypeScript hook's own launcher, and all 227 cases passed (the base, 10 Nov). On the base's stubs all 227 fail.

### 9.4 What the replay cannot hold

- `fixtures/hook-cases/manual-calls.json`: a recorded call a test made with its own dependencies, which no process can make (one: Command Code's derived token file with the fake daemon's folder named as derm's own). The replay skips it; lane 5bA ports it as a Rust test in its folder.
- `fixtures/hook-cases/manual.json`: the 72 TypeScript cases that make no hook call (registration lines, plugin files and launchers, server-name readers, preset agreement, the core copies), each with its lane: 5bA 16, 5bB 17, 5bF 33, integration 2 (the switch-over), the base 4 (ported here: `derm_core::redact::hook`, `gate::core`, `gate::daemon` and `hook` tests). Each lane ports its own as Rust tests in its folder and names them in its status doc; integration's switch-over table (wave 5b plan section 6) checks every line.
